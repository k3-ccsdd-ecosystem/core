# 制約（小項目 1-6）

## 入力

- 引数: `$ARGUMENTS`。最初の語は小項目 ID（`1-6`）、残りが外部の条件（法規、予算、契約条件）
- インプット: `docs/01-planning/concept.md`、`docs/01-planning/research.md`、既存システムの更改なら `docs/01-planning/as-is.md`
- 対応表: `.ccsdd/docs/stages/stage-01.md`
- テンプレート: `.ccsdd/templates/spec/01-planning/constraints.md` → 出力: `docs/01-planning/constraints.md`

## 手順

1. `git branch --show-current` で作業ブランチを確かめる。`stage-1` でなければ `git switch stage-1`、無ければ `git switch -c stage-1 main`
2. テンプレートの 7 観点（CST-1〜CST-7）を、インプットと外部の条件から 1 行ずつ埋める
   - 「内容」: 決まっている制約。制約が無ければ「制約なし（理由）」。インプットから決められなければ「未確定」と書き、「未確定の制約」にも載せる
   - 「根拠・出典」: どのインプットのどこから導いたか、外部の条件の出所
   - 「後工程への影響」: どの段階で何を決めるときに効くか（例: 認証方式 → 段階 4 の API 契約、段階 7 のセキュリティ基準）
   - 「影響する段階」: 段階番号をカンマ区切りで
3. 7 観点に収まらない制約（性能の下限、対応端末、運用時間など）が見つかれば、CST-8 から行を足す
4. 後工程への影響を指摘する: 後の段階で手戻りを生みやすい制約（認証、データ所在、予算）は、影響する段階を漏らさない。予算上限と法規は段階 7 の非機能要件（コスト上限、法規・契約）に継承される
5. セルフレビューし、`node .ccsdd/gate-checker/dist/gate-check.mjs --stage 1 --no-write` で自分の成果物への指摘が無いことを確かめる
6. `docs/01-planning/constraints.md` だけを `git add` し、`docs: 1-6 制約一覧` でコミットする
7. 報告する: 未確定の制約と確定に要る情報、暫定で決めたこと

## セルフレビューの観点

- 共通: 人が読める体裁、テンプレートの節と表がそろっている、記入欄が残っていない、「参照元」のパスが存在する
- 7 観点の行がすべてあり、ID が CST-1 から連続している（追加分は続きから）
- 「制約なし」に理由がある。「未確定」が「未確定の制約」と対応している
- 企画書のスコープ外・調査メモの示唆と矛盾していない
