# UX 設計（小項目 2-1〜2-4）

## 入力

- 引数: `$ARGUMENTS`。最初の語が小項目 ID（`2-1`〜`2-4`）、残りが補足。小項目 ID が無ければ、2-1 → 2-2 → 2-3 → 2-4 のうち成果物がまだ無い最初の小項目だけを行う
- 前提: GATE-1 の判定記録（`gates/gate-1.md`）が main にマージ済み。無ければ作業せず報告する
- 対応表: `.ccsdd/docs/stages/stage-02.md`
- 守る規約: `.claude/rules/`（特に documents.md、ids.md、git-issue-pr.md）

## 手順（共通）

1. `git branch --show-current` で作業ブランチを確かめる。`stage-2` でなければ `git switch stage-2`、無ければ `git switch -c stage-2 main`
2. 下の「小項目ごとの手順」を、指定された小項目についてだけ行う
3. 「セルフレビューの観点」で見直し、直す
4. `node .ccsdd/gate-checker/dist/gate-check.mjs --stage 2 --no-write` を実行し、自分の成果物への指摘が無いことを確かめる（まだ作っていない小項目に関する指摘、例: 2-2 の時点の「全ストーリーに画面」は残ってよい）
5. 成果物だけを `git add` し、`docs: <小項目 ID> <成果物名>` でコミットする
6. 報告する: 作った・直したファイルと ID、gate-checker の結果、未確定事項、暫定で決めたこと

## 小項目ごとの手順

### 2-1 ペルソナとジャーニー

- テンプレート: `.ccsdd/templates/spec/02-ux/personas.md` → 出力: `docs/02-ux/personas.md`
- インプット: `docs/01-planning/concept.md`、`docs/01-planning/constraints.md`
- 手順:
  1. 企画書の「対象ユーザー」ごとに 1 人以上のペルソナを `### PER-<n>: 名前` で定義する。属性は企画書と制約から導き、関係する制約を `CST-n` で書く
  2. 各ペルソナのジャーニーを `### ジャーニー: PER-<n>` の下に表で書く（認知から日常利用まで、接点と課題・機会）
  3. 「企画書との対応」で、対象ユーザー・ペルソナ・価値仮説の対応を表にする。対応しない対象ユーザーや価値仮説があれば理由を書き、企画書との不整合として報告する

### 2-2 ユーザーストーリーと受け入れ条件

- テンプレート: `.ccsdd/templates/spec/02-ux/stories/US-n.feature` → 出力: `docs/02-ux/stories/US-<n>.feature`（1 ストーリー 1 ファイル）
- インプット: `docs/02-ux/personas.md`、`docs/01-planning/concept.md`
- 手順:
  1. ジャーニーの課題・機会から、ペルソナが達成したいことをストーリーにする。1 ストーリーは 1 つの価値を持ち、段階 3 以降で独立して作れる大きさにする
  2. ID を採番する: 既存の `US-<n>` の最大値 + 1。ファイル名と Feature のタグを同じ ID にする
  3. Feature の説明に「<ペルソナ名> として、<したいこと>。なぜなら <得たい価値>。」と「関係する制約: CST-n」を書き、Feature のタグに `@PER-<n>` を付ける
  4. 受け入れ条件を Scenario で書く。各 Scenario に `@US-<n>-AC<m>` を付け、When と Then を 1 つ以上書く。Then は画面やデータで観察できる結果にする。正常系に加えて、主な失敗・境界の場合を 1 つ以上入れる
  5. 構文は gate-checker の Gherkin の検査で確かめる

### 2-3 画面遷移

- テンプレート: `.ccsdd/templates/spec/02-ux/screens.md` → 出力: `docs/02-ux/screens.md`
- インプット: `docs/02-ux/stories/`、`docs/02-ux/personas.md`
- 手順:
  1. ストーリーの When / Then に現れる画面を洗い出し、「画面一覧」に `SCR-<n>` で定義する。各行の「ストーリー」に、その画面を使うストーリーの ID を列挙する
  2. 全ストーリーが、画面一覧のどれかの行で参照されることを確かめる
  3. 「遷移」に、遷移元・遷移先・契機・ストーリーを書く。起点は「（起動）」のように書く
  4. 任意で「遷移図」を Mermaid で描く（ノード名にハイフンを使えないため、`SCR1["SCR-1 画面名"]` のようにラベルに ID を書く）
  5. 画面のレイアウトや要素は書かない（段階 3 の画面仕様で決める）

### 2-4 MVP スライス

- テンプレート: `.ccsdd/templates/spec/02-ux/mvp.md` → 出力: `docs/02-ux/mvp.md`
- インプット: `docs/02-ux/stories/`、`docs/01-planning/concept.md`、`docs/01-planning/constraints.md`
- 手順:
  1. 「優先度の基準」を書く。既定: 価値仮説の検証に要る、または制約上外せないストーリーは Must、検証を強めるものは Should、無くても検証できるものは Could、今回作らないものは Won't
  2. 全ストーリーを「スライス」の表に 1 行ずつ載せ、優先度、MVP に含むか、対応する価値仮説（「仮説 n」）、関係する制約、理由を書く
  3. 「MVP の狙い」に、この MVP でどの価値仮説をどう検証するかを書く。MVP に含むストーリーで価値仮説を検証できない場合は、不足として報告する

## セルフレビューの観点

- 共通: 人が読める体裁、テンプレートの節と表がそろっている、記入欄が残っていない、「参照元」のパスが存在する、ID の形式と採番（`.claude/rules/ids.md`）
- 2-1: 企画書の全対象ユーザーにペルソナがあり、全ペルソナにジャーニーがある
- 2-2: 全ストーリーにペルソナの参照と受け入れ条件がある。Scenario が 1 つの振る舞いを確かめ、Then が観察できる。実装の詳細（API、DB）を受け入れ条件に書いていない
- 2-3: 全ストーリーに画面がある。全画面がストーリーを参照する。到達できない画面が無い
- 2-4: 全ストーリーが分類されている。MVP に含むストーリーで価値仮説を検証できる。制約一覧の制約（認証など）に要るストーリーを落としていない
