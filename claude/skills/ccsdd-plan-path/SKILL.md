# 計画（小項目 1-7）

## 入力

- 引数: `$ARGUMENTS`。最初の語は小項目 ID（`1-7`）、残りが規模・リスクの補足
- インプット: `docs/01-planning/concept.md`、`docs/01-planning/constraints.md`、既存システムの更改なら `docs/01-planning/as-is.md`
- 対応表: `.ccsdd/docs/stages/stage-01.md`。各段階の内容は `.ccsdd/docs/stages/` と `.ccsdd/docs/gates.md`
- テンプレート: `.ccsdd/templates/spec/01-planning/plan-path.md` → 出力: `docs/01-planning/plan-path.md`

## 手順

1. `git branch --show-current` で作業ブランチを確かめる。`stage-1` でなければ `git switch stage-1`、無ければ `git switch -c stage-1 main`
2. 「開発パターン」を「新規」か「既存」で書く（既存のリポジトリ・稼働環境を更改するなら「既存」）。規模（利用者数、画面数、連携先の数の見込み）とリスクを書く
3. 12 段階それぞれの「適用」を、下の選択基準で「実施」「縮小」「省略」から選び、理由を書く。縮小・省略は、それで困らない根拠（どの制約・企画の前提によるか）を書く
4. 「選択の基準」に、使った基準と、基準から外れた判断があればその理由を書く
5. セルフレビューし、`node .ccsdd/gate-checker/dist/gate-check.mjs --stage 1 --no-write` で自分の成果物への指摘が無いことを確かめる
6. `docs/01-planning/plan-path.md` だけを `git add` し、`docs: 1-7 計画パス` でコミットする
7. 報告する: 縮小・省略した段階と理由、暫定で決めたこと

## 選択基準（v0.1 の既定）

| 条件 | 選択 |
|---|---|
| 段階 1・2・12 | 常に実施 |
| 段階 8（インフラ設計・構築） | 常に実施（インフラを飛ばさない） |
| 外部連携先が無い（制約一覧の CST「外部連携先と試験環境の有無」） | 10 を縮小（外部結合試験は自システムのみ） |
| 利用者が少なく性能目標を置かない | 7 と 9 を縮小（性能・アラートは最小限） |
| 認証・個人情報を扱う（制約一覧の認証方式・法規） | 11 を実施（縮小しない） |
| 既存システムの更改で、既存の API 契約をそのまま使う | 4 を縮小（差分だけを決める） |

v0.1 の完了条件は省略・縮小を読まない（判定は実施する前提で検査する）。省略した段階の判定は、判定記録に「省略（計画パスによる）」と書いて人が判定する。

## セルフレビューの観点

- 共通: 人が読める体裁、テンプレートの節と表がそろっている、記入欄が残っていない、「参照元」のパスが存在する
- 12 段階すべての行があり、適用が「実施 / 縮小 / 省略」のいずれか
- 縮小・省略の理由が、制約一覧や企画書の記述に結び付いている
- 開発パターンが現状調査報告の有無と一致している（既存なのに現状調査報告が無い、を見逃さない）
