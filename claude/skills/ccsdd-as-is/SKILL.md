# 現状把握（小項目 1-5）

## 入力

- 引数: `$ARGUMENTS`。最初の語は小項目 ID（`1-5`）、残りが調査対象（既存リポジトリの URL またはローカルパス、稼働環境、既存文書の所在）
- 調査対象が引数に無ければ、成果物を作らずに報告で所在を求める
- 対応表: `.ccsdd/docs/stages/stage-01.md`
- テンプレート: `.ccsdd/templates/spec/01-planning/as-is.md` → 出力: `docs/01-planning/as-is.md`

## 手順

1. `git branch --show-current` で作業ブランチを確かめる。`stage-1` でなければ `git switch stage-1`、無ければ `git switch -c stage-1 main`
2. 調査範囲を決め、「調査範囲と方法」に書く（調べないものも書く）
3. リポジトリ構造と依存関係を解析する: ディレクトリ構成、パッケージの定義ファイル（`package.json`、`pom.xml`、`go.mod` など）、CI の設定、IaC、README。調査時のコミットを「参照元」に書く
4. 「構成」「技術スタック」（層、技術、バージョン）を書く。バージョンは定義ファイルから取り、推測しない
5. 文書の所在を判定し、「設計書の有無」に文書ごとの所在と状態（最新 / 古い / 無い）を書く
6. 開発の実践（ブランチ運用、レビュー、テスト、CI / CD、リリース）を、設定ファイルから読める事実と、聞き取りが要る事項に分けて書く。対話セッションなら利用者に聞き取り、ヘッドレス実行なら聞き取りが要る事項を「未確定」として列挙する
7. 「後工程への影響」に、制約一覧（1-6）と計画パス（1-7）へ持ち込むことを書く
8. セルフレビューし、`node .ccsdd/gate-checker/dist/gate-check.mjs --stage 1 --no-write` で自分の成果物への指摘が無いことを確かめる（計画パスの開発パターンが「既存」でないと、この成果物は「対象外」と表示される）
9. `docs/01-planning/as-is.md` だけを `git add` し、`docs: 1-5 現状調査報告` でコミットする
10. 報告する: 調査範囲、未確定事項（聞き取りが要る事項）、暫定で決めたこと

## 守ること

- 秘密情報（`.env`、鍵、接続文字列、トークン）を読まない・書かない（`.claude/rules/security.md`）
- 既存リポジトリを変更しない（読むだけ）

## セルフレビューの観点

- 共通: 人が読める体裁、テンプレートの節と表がそろっている、記入欄が残っていない
- 事実（定義ファイル・設定から読めたこと）と推測・聞き取り待ちを分けている
- 技術スタックのバージョンに根拠がある
- 後工程への影響が、制約一覧の 7 観点（認証方式、データ所在、マルチテナント、リアルタイム性、予算上限、法規、外部連携先と試験環境の有無）に照らして漏れていない
