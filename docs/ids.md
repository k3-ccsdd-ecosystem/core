# ID 規約

成果物の設計要素に付ける ID の規約。段階ごとの成果物 ID の連鎖（ストーリー → 画面 → API → シーケンス → 試験）でトレーサビリティを取るために使う。gate-checker はこの規約（`gate-checker/rules/ids.json`）で ID を検査する。

この文書の構成:

1. 形式と接頭辞
2. 採番
3. 定義と参照の書き方
4. Issue・PR・コミットでの書き方
5. 段階をまたぐ参照

## 1. 形式と接頭辞

- 形式は「接頭辞-連番」。連番は 1 から始まる 10 進数で、ゼロ埋めしない（`CST-1`、`CST-12`。`CST-01`、`CST-0` は不可）
- 受け入れ条件は「`US-<n>-AC<m>`」（例: `US-3-AC2`）。n はストーリーの連番、m はそのストーリー内の連番
- 判定記録は「`GATE-<段階番号>`」（`GATE-1`〜`GATE-12`）。連番ではなく段階番号を使う
- 接頭辞は大文字。小文字（`us-1`）や別の区切り（`US_1`、`US1`）は ID として扱わない

| 接頭辞 | 対象 | 定義する小項目 | 定義する場所 |
|---|---|---|---|
| `CST` | 制約 | 1-6 | spec の `docs/01-planning/constraints.md`「制約一覧」の表 |
| `PER` | ペルソナ | 2-1 | spec の `docs/02-ux/personas.md` の見出し |
| `US` | ユーザーストーリー | 2-2 | spec の `docs/02-ux/stories/US-<n>.feature` の Feature のタグ |
| `US-<n>-AC<m>` | 受け入れ条件 | 2-2 | 同じファイルの Scenario のタグ |
| `SCR` | 画面 | 2-3 | spec の `docs/02-ux/screens.md`「画面一覧」の表 |
| `API` | API | 段階 4 | be（雛形の作成時に決める） |
| `SEQ` | シーケンス | 段階 5 | be（雛形の作成時に決める） |
| `NFR` | 非機能要件 | 段階 7 | infra（雛形の作成時に決める） |
| `RES` | リソース | 段階 8 | infra（雛形の作成時に決める） |
| `SLI` | SLI | 段階 9 | infra（雛形の作成時に決める） |
| `ALT` | アラート | 段階 9 | infra（雛形の作成時に決める） |
| `THR` | 脅威 | 段階 11 | infra（雛形の作成時に決める） |
| `E2E` | E2E 試験シナリオ（ローカルの FE + BE） | 段階 6 | fe（雛形の作成時に決める） |
| `TST` | 試験シナリオ（実環境試験） | 段階 10 | infra（雛形の作成時に決める） |
| `GATE` | 判定記録 | 各段階の判定 | 各リポジトリの `gates/gate-<段階番号>.md` の題（`# GATE-1: 追求判定`） |

## 2. 採番

- 連番は、リポジトリ内で接頭辞ごとに一意にする
- 新しい ID は、その接頭辞で使った最大の連番 + 1 にする
- 欠番は詰めない。削除した ID は再利用しない（過去の Issue・PR の参照先が別物になるのを防ぐ）
- ID を削除するときは、先にその ID への参照を消すか置き換える（残った参照は gate-checker が「未解決の参照」として検出する）
- 受け入れ条件の m はストーリーごとに 1 から振る

## 3. 定義と参照の書き方

ID を新しく作る位置を「定義」、別の位置から ID を指すことを「参照」と呼ぶ。定義は ID ごとに 1 か所だけにする。

### Markdown

定義になる位置は次の 2 つ。それ以外の位置に書いた ID はすべて参照になる（定義と同じ文書の中でも）。

| 定義の位置 | 例 | 定義の範囲（参照の検査に使う） |
|---|---|---|
| 見出しの先頭 | `### PER-1: 佐藤さん` | その見出しの節 |
| 第 1 列の見出しが `ID` の表の、第 1 列 | `\| CST-1 \| 認証方式 \| … \|` | その行 |

- 定義になるのは、その接頭辞を定義する文書（1 の表の「定義する場所」）の中だけ。他の文書の見出しや `ID` 列に書いた ID は参照として扱う
- 参照を並べる表の第 1 列の見出しは `ID` にしない。「ストーリー」「画面」など内容を表す名前にする
- 見出しで参照するときは ID を先頭に置かない（`### ジャーニー: PER-1`。`### PER-1 のジャーニー` は定義の重複になる）
- 範囲の表記（`US-1〜3`、`US-1-3`）は使わず、ID を列挙する（`US-1, US-2, US-3`）
- HTML コメント（`<!-- -->`）の中の ID は検査しない

### Gherkin（.feature）

```gherkin
@US-2 @PER-1
Feature: ToDo を追加する
  佐藤さん として、やることを 1 行で追加したい。なぜなら 忘れる前に書き留めたいから。

  関係する制約: なし

  @US-2-AC1
  Scenario: 1 行入力して Enter で追加できる
    Given ログインして一覧画面を開いている
    When 入力欄に「牛乳を買う」と入力して Enter を押す
    Then 一覧の先頭に「牛乳を買う」が追加される
```

- 1 ストーリー 1 ファイル。ファイル名は `US-<n>.feature`
- Feature のタグ `@US-<n>` がストーリーの定義（ちょうど 1 つ）、`@PER-<n>` はペルソナの参照（1 つ以上）
- Scenario のタグ `@US-<n>-AC<m>` が受け入れ条件の定義（ちょうど 1 つ。n は Feature と同じ）
- Gherkin のキーワードは英語（`Feature` `Scenario` `Given` `When` `Then` `And` `But` `Background` `Rule`）、本文は日本語で書く
- `#` で始まるコメント行の ID は検査しない

### gate-checker が検査すること

| 検査 | 内容 |
|---|---|
| ID の形式 | 接頭辞に続く ID 候補が 1 の形式に合うか |
| ID の重複 | 同じ ID が 2 か所以上で定義されていないか |
| ID 参照の解決 | 参照した ID の定義が検査対象の文書にあるか |
| 対応（段階ごとの完了条件） | 例: 全ストーリーが画面一覧で参照されているか、全画面がストーリーを参照しているか（[gates.md](./gates.md)） |

## 4. Issue・PR・コミットでの書き方

- Issue のタイトルは「`<ID>: <要約>`」にする（例: `US-2: 空の入力を拒否する受け入れ条件を追加`）。ID が複数あるときは主な ID をタイトルに、残りを本文に書く
- PR の本文に、その PR が作る・変える・満たす ID を `Refs:` の行に半角スペース区切りで並べる（例: `Refs: US-2 US-2-AC2 SCR-2`）。Issue を閉じる場合は `Closes #<番号>` を別の行に書く
- 判定記録の PR のタイトルは「`GATE-<n>: <判定名>`」、本文の `Refs:` には `GATE-<n>` と、その段階で定義した ID を並べる
- コミットメッセージは「`<type>: <要約>`」（type は `docs` `feat` `fix` `test` `chore` `ci`）。小項目の成果物は「`docs: <小項目 ID> <成果物名>`」（例: `docs: 1-6 制約一覧`）にする。コミットメッセージの ID は任意（記録の正は PR の `Refs:`）

## 5. 段階をまたぐ参照

- 接頭辞ごとに、定義するリポジトリは 1 つに決まる（1 の表）。判定記録も段階番号が付くため、`GATE-<n>` は製品全体で一意になる。このため、他リポジトリの ID も接頭辞と連番だけで参照する（リポジトリ名を付けない）
- 他リポジトリの ID を参照する段階では、入力記録（`templates/common/inputs.md`）の「参照する ID」に、その ID と固定したコミットを書く
- 前段階の ID の追加・変更が必要になったら、定義するリポジトリへ Issue を出す（タイトルは「`<ID>: <要約>`」）。受け取り側は変更のマージ後に入力記録の固定先を更新する
