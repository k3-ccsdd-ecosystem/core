# 判定と完了条件

各段階の終わりの判定（追求判定、UX 承認など）の進め方、判定記録の形式、判定の前に機械チェックする完了条件を定める。完了条件の正は `gate-checker/rules/stage-<n>.json` で、この文書はその説明。

パスの書き方: `templates/…` と `gate-checker/…` は core の中のパス。製品リポジトリでは `sync-core.sh` がそれぞれ `.ccsdd/templates/…`、`.ccsdd/gate-checker/…` にコピーする。`docs/…`（成果物）と `gates/…` は製品リポジトリの中のパス。

この文書の構成:

1. 判定の流れ
2. 判定記録（`gates/gate-<n>.md`）
3. 機械チェックの結果（`gates/gate-<n>.result.json`）
4. gate-checker の使い方
5. 段階 1 の完了条件（GATE-1 追求判定）
6. 段階 2 の完了条件（GATE-2 UX 承認）
7. 完了条件の書き方（`rules/stage-<n>.json`）

## 1. 判定の流れ

AI が成果物を作って機械チェックとレビューを済ませ、人が判定し、PR のマージで確定する。

| # | 誰が | 何をする |
|---|---|---|
| 1 | AI（各段階の skill） | 段階の作業ブランチ `stage-<n>` で成果物を作り、小項目ごとにコミットする |
| 2 | AI（`ccsdd-gate` skill） | gate-checker を実行して `gates/gate-<n>.result.json` を書き、reviewer エージェントにレビューさせ、判定記録 `gates/gate-<n>.md` の「対象」「機械チェック結果」「引き渡し物」を書く |
| 3 | AI（`ccsdd-gate` skill） | 判定記録をコミットし、PR（タイトル `GATE-<n>: <判定名>`）を作る |
| 4 | 人（判定者） | 判定記録の「人の判定」を書く（PR 上で編集するか、判定を伝えて skill に転記させる） |
| 5 | CI | `gate-check --stage <n> --record --no-write` で、成果物と判定記録の両方を検査する |
| 6 | 人（判定者） | PR をマージする。マージで判定が確定する |

判定の値と次の動き:

| 判定 | 意味 | 次の動き | 機械チェックの合格 |
|---|---|---|---|
| Go | 完了条件を満たし、次段階へ進む | 次段階の最初の小項目へ | 必要 |
| 条件付き Go | 条件を満たす前提で次段階へ進む | 条件を Issue にし、判定記録の「条件」に Issue を書く | 必要 |
| 保留 | 判断材料が足りない | 不足を Issue にし、同じ段階で再判定する | 不要 |
| No-Go | 進めない | 理由を記録する。企画の中止、または前段階のリポジトリへ Issue を出す | 不要 |

## 2. 判定記録（`gates/gate-<n>.md`）

テンプレートは `templates/common/gate.md`。題は「`# GATE-<n>: <判定名>`」。

| 節 | 書く内容 | 書く人 |
|---|---|---|
| 対象 | 機械チェックをかけた成果物のパスと、そのときのコミット（結果 JSON の `commit`） | AI |
| 機械チェック結果 | 実行日時、ツールのバージョン、合否、検査ごとの結果と指摘の要約、生データのパス。小節「AI レビューの所見」に reviewer の所見（判定の参考で、機械チェックではない） | AI |
| 人の判定 | `- 判定:`（Go / 条件付き Go / 保留 / No-Go）、`- 判定者:`、`- 日付:`（YYYY-MM-DD）、`- 条件:`、`- 理由:` | 人 |
| 引き渡し物 | 次段階が入力記録で固定する参照先（成果物名、パス、受け取る段階） | AI |

## 3. 機械チェックの結果（`gates/gate-<n>.result.json`）

gate-checker が書く。判定記録の「機械チェック結果」の生データ。

| フィールド | 内容 |
|---|---|
| `schemaVersion` | 形式の版（1） |
| `tool` | `name` と `version` |
| `stage` / `gate` / `title` | 段階番号、判定記録の ID、判定名 |
| `mode` | `artifacts`（成果物のみ）または `record`（判定記録も検査） |
| `checkedAt` | 実行日時（ISO 8601、UTC） |
| `commit` / `dirty` | 対象リポジトリの HEAD と、未コミットの変更の有無（git 管理外なら `null`） |
| `rules` | 使った完了条件のファイル名 |
| `passed` | 合否（不合格の検査が 1 つも無ければ `true`） |
| `summary` | 検査数、不合格数、対象外数、エラー数、警告数 |
| `checks` | 検査ごとの `id`、`title`、`target`、`status`（`pass` / `fail` / `skip`）、`reason`、`findings`（`code`、`severity`、`message`、`file`、`line`） |
| `ids` | 定義された ID の一覧（種類ごと） |

## 4. gate-checker の使い方

```bash
# core で
npm run gate-check -- --stage 1 --root <対象リポジトリ>

# 製品リポジトリで（sync-core.sh でコピーした実行物）
node .ccsdd/gate-checker/dist/gate-check.mjs --stage 1 --root .
```

| オプション | 内容 |
|---|---|
| `--stage <n>` | 段階番号（必須） |
| `--root <path>` | 対象リポジトリのルート（既定: カレントディレクトリ） |
| `--rules-dir <dir>` | 完了条件のディレクトリ（既定: CLI の位置から見た `../rules`） |
| `--record` | 判定記録も検査する（人の判定の記入後に CI で使う） |
| `--no-write` | 結果 JSON を書かない |
| `--json` | 結果 JSON を標準出力に出す |

終了コード: 0 = 合格、1 = 不合格、2 = 引数・完了条件の誤り。

## 5. 段階 1 の完了条件（GATE-1 追求判定）

小項目 1-8 の「必須節、制約一覧の観点の網羅」を次の検査で確かめる。成果物の置き場とテンプレートは [stages/stage-01.md](./stages/stage-01.md)。

すべての成果物に共通: ファイルがある、記入欄 `{{...}}` が残っていない、必須節があり空でない、「参照元」に書いたパスが存在する。

| 成果物 | 必須節 | 追加の検査 |
|---|---|---|
| 1-2 ブレスト記録 | 参照元、着想と課題、背景、発散したアイデア、絞り込み、未解決の問い | 発散したアイデアが 3 件以上 |
| 1-3 企画書 | 参照元、コンセプト、対象ユーザー、解決する課題、価値仮説、検証の問答、スコープ外 | 対象ユーザー・価値仮説の表が埋まっている。検証の問答が 3 件以上 |
| 1-4 調査メモ | 参照元、調査の問い、類似事例、技術、示唆、出典 | 類似事例・技術の各行に出典がある |
| 1-5 現状調査報告 | 参照元、調査範囲と方法、構成、技術スタック、設計書の有無、開発の実践、後工程への影響 | 計画パスの開発パターンが「既存」のときだけ必須（「新規」なら対象外） |
| 1-6 制約一覧 | 参照元、制約一覧、未確定の制約 | 7 つの観点（認証方式、データ所在、マルチテナント、リアルタイム性、予算上限、法規、外部連携先と試験環境の有無）の行がそろい、全列が埋まっている |
| 1-7 計画パス | 参照元、開発パターン、段階の選択、選択の基準 | 開発パターンが「新規」か「既存」。12 段階すべての行があり、適用が「実施 / 縮小 / 省略」で理由がある |

ID の検査（対象: `docs/01-planning/**/*.md`）: 形式、重複、参照の解決（`CST` の定義は制約一覧）。

## 6. 段階 2 の完了条件（GATE-2 UX 承認）

小項目 2-5 の「全ストーリーに受け入れ条件と画面、Gherkin 構文、ID の重複」を次の検査で確かめる。成果物の置き場とテンプレートは [stages/stage-02.md](./stages/stage-02.md)。

| 成果物 | 必須節 | 追加の検査 |
|---|---|---|
| 2-1 ペルソナとジャーニー | 参照元、ペルソナ、ジャーニー、企画書との対応 | ジャーニー・企画書との対応の表が埋まっている |
| 2-2 ユーザーストーリー（`stories/US-<n>.feature`） | — | 1 ファイル以上。Gherkin の構文が正しい。Feature に `@US-<n>` がちょうど 1 つでファイル名と一致。Scenario が 1 つ以上で、各 Scenario に `@US-<n>-AC<m>` がちょうど 1 つ（n は Feature と同じ）。各 Scenario に When と Then がある |
| 2-3 画面遷移 | 参照元、画面一覧、遷移 | 画面一覧・遷移の表が埋まっている |
| 2-4 MVP スライス | 参照元、優先度の基準、スライス、MVP の狙い | 優先度が Must / Should / Could / Won't、MVP が「含む / 含まない」。全列が埋まっている |

ID の検査（対象: 段階 1・2 の文書と `.feature`）:

| 検査 | 内容 | 重大度 |
|---|---|---|
| 形式・重複・参照の解決 | 段階 1 と同じ。`CST`・`PER`・`US`・`US-<n>-AC<m>`・`SCR` が対象 | エラー |
| 全ストーリーがペルソナを参照 | 各 `.feature` に `PER` の参照がある | エラー |
| 全ストーリーに画面 | 各 `US` が画面遷移の「画面一覧」で参照されている | エラー |
| 全ストーリーが MVP スライスで分類済み | 各 `US` が MVP スライスの「スライス」で参照されている | エラー |
| 全画面がストーリーを参照 | 画面一覧の各行に `US` の参照がある | エラー |
| 全ペルソナにジャーニー | 各 `PER` がペルソナとジャーニーの「ジャーニー」で参照されている | エラー |
| 全ペルソナがストーリーで使われている | 各 `PER` がどれかの `.feature` で参照されている | 警告 |

## 7. 完了条件の書き方（`rules/stage-<n>.json`）

完了条件は宣言的に書き、gate-checker のコードは段階に依存させない。型の正は `gate-checker/src/types.ts`。

| キー | 内容 |
|---|---|
| `stage` / `gate` / `title` | 段階番号、判定記録の ID、判定名 |
| `scan` | ID を検出するファイルの glob |
| `artifacts[]` | Markdown の成果物。`path`、`template`、`subitem`、`required` または `requiredWhen`（別ファイルの `- キー: 値` が一致するときだけ必須）、`sections`（必須節）、`tables`（節・必須列・空欄を許さない列・最小行数・列の値の網羅・列ごとに許す値）、`fields`（`- キー: 値` の値の候補・形式）、`sourceSection`（パスの存在を検査する節） |
| `gherkin[]` | `.feature` の検査。`files`、Feature と Scenario で定義する ID の種類、ファイル名との一致、最小の Scenario 数、必要なステップの種類 |
| `definitions[]` | ID の種類と、それを定義する文書の glob |
| `coverage[]` | ID の対応。`each`（対象の種類）に対し、`referencedIn` + `inSection`（どこかで参照されている）または `contextReferences`（定義の範囲に別の種類の参照がある）。`severity` で警告にできる |
| `record` | 判定記録の検査（`--record` のとき）。`artifacts[]` と同じ項目に加え、`decisionKey` と、機械チェックの合格を前提とする判定の値 |

完了条件を変えたら、対応するテンプレート（`templates/`）とこの文書を合わせて直す。テンプレートと完了条件のずれは `gate-checker/test/templates.test.ts` が検出する。
